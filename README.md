# Construction Intelligence Platform

An enterprise-grade, autonomous AI/ML-powered Construction Planning, Progress Monitoring, Critical Path Method (CPM) Scheduling, and Risk Prediction Engine.

---

## 🌟 Key Features

- **Automated CPM Scheduling Engine**: Forward/backward pass critical path analysis, total/free float computation, and dependency resolution.
- **Predictive Machine Learning**: 
  - Activity duration estimation
  - Schedule delay probability & risk classification (Low / Medium / High / Critical)
  - Daily productivity forecasting
  - Labour shortage predictions & material variance tracking
- **Geotechnical & Environmental Risk Analysis**: Automated parsing and integration of geotechnical reports (SBC, rock types, groundwater levels, soil strata).
- **Daily Progress Tracking & Engineer Validation**: Daily logs, multi-stage checklist verification, and variance detection.
- **Interactive Modern Dashboard**: React 19 + TypeScript + Vite dashboard with responsive KPI metrics, Gantt/CPM charts, blocker trackers, and real-time status.

## 🚀 Quickstart Guide

### Prerequisites
- **Python**: 3.10–3.12 (tested on 3.11; pinned `scikit-learn`/`numpy` do not build on Python 3.13+)
- **Node.js**: 18+ and npm (tested on Node 22)
- **Git**

---

### 1. Backend Setup & Run

1. Open a terminal in the project root:
   ```bash
   cd Construction-1
   ```

2. Create and activate a Python virtual environment:
   - **Windows**:
     ```powershell
     python -m venv venv
     .\venv\Scripts\activate
     ```
   - **Linux / macOS**:
     ```bash
     python3 -m venv venv
     source venv/bin/activate
     ```

3. Install backend dependencies:
   ```bash
   pip install -r backend/requirements.txt
   ```

4. Create the local SQLite database (`construction_intelligence.db` is git-ignored, so generate it on first setup; re-run to rebuild or re-train from scratch):
   ```bash
   python seed_data.py
   python train_models.py
   ```

5. *(Optional for local dev, required in production)* Configure security via environment variables:
   - `SECRET_KEY`: JWT signing key. Must be set when `APP_ENV=production` (the app refuses to start otherwise).
   - `APP_ENV`: `development` (default) or `production`.
   - `CORS_ORIGINS`: comma-separated allowed frontend origins (default `http://localhost:5173,http://127.0.0.1:5173`).

   Every API route except `/health`, `/api/auth/login`, `/api/auth/token` and the API-key based `/api/v1/geotechnical` endpoints requires a signed-in user. Creating users (`POST /api/auth/register`) is Admin only.

   **Project access:** besides signing in, users must be members of a project (table `project_members`) and only see the towers in their scope (`ALL`, or a tower such as `Tower A`). Admin and Top Management reach every project. After upgrading an existing database run `python scripts/seed_zoy_members.py` once to grant the current users access to 41 ZOY. Admins and project managers manage members through `/api/projects/{id}/members`.

   **Schedule import:** `POST /api/projects/{id}/schedule/import` (Admin, Project Manager or Planning Engineer) loads activities, baseline dates and dependencies from the Excel template in `data/zoy/41_ZOY_schedule_sample.xlsx` (sheet `Schedule`; regenerate it with `python scripts/generate_zoy_sample_schedule.py`). It is all-or-nothing: any file error returns 422 with the full list and writes nothing. Add `dry_run=true` to validate only. The baseline is never overwritten silently: re-importing needs `new_baseline=true`, and replacing a project's existing activities needs an Admin and `replace_existing=true`.

   **Tasks:** site teams create execution tasks against a planned activity (`POST /api/projects/{id}/tasks`). Planned tasks go `DRAFT -> IN_PROGRESS -> COMPLETED` (and can be blocked); unplanned tasks need a reason and PM approval (`submit`, `approve` / `reject`) before they can be started. Approval never starts work. An activity's progress is derived from its tasks, weighted by planned days, and never changes the baseline.

   **Readiness checks:** each planned task gets a checklist copied from the template for its type of work (slab, excavation, blockwork, waterproofing, MEP, finishing, general). Mandatory checks must be done before the task can start; a Project Manager can skip one check for one task with a reason. Admin, Planning Engineer or Quality Manager edit the templates through `/api/readiness-templates`. The checks are step-locked like a pilot's checklist: they are done in the listed order, a step opens only when every earlier mandatory step is done or waived (optional steps never hold up the next one), and unticking a step clears the ticked steps after it.

   **The app screens:** everyday work lives in three pages. Engineers see *My tasks* and *Schedule*; project managers see *Overview*, *Tasks* and *Schedule*; Top Management sees *Overview*, *Schedule* and *Reports*. The earlier detailed pages are still there under *More tools* (Admin and Project Manager).

   **Demo sign-in:** with `DEMO_MODE=true` (the default in development; set `DEMO_MODE=false` to hide it; always off when `APP_ENV=production`, whatever `DEMO_MODE` says) the sign-in screen lists roles (Site Engineer Tower A / Tower B, Project Manager, Director, Admin); tapping one signs in as that role's account. Passwords never reach the browser. Sign out (top right) returns to the role list. The email and password form remains under "Sign in with email instead". Run `python scripts/seed_zoy_members.py` once so the two engineer accounts exist.

   **Problems and delay:** anything holding up the work is reported as a problem (`POST /api/projects/{id}/problems`), optionally from a running task, which then becomes blocked. The system estimates the effect from the dependency network and float; a Project Manager confirms or adjusts it (`POST /api/problems/{id}/impact`). A reported problem is not a delay: `GET /api/projects/{id}/delay-summary` and the Overview page count only confirmed delay, and show unreviewed problems separately. Resolving a problem releases its task. Older hindrance-register entries stay visible as "impact not reviewed".

   **41 ZOY+ and the plan sequence:** `python scripts/build_zoy_baseline_from_msp.py` builds `data/zoy/41_ZOY_baseline_master_2026-10-06.xlsx` from the MSP master schedule tracker (real IDs, dates and predecessors; links to rows the PDF hides are re-pointed and listed on the Read Me sheet). `python scripts/seed_41zoy_plus.py` creates the "41 ZOY+" project from it, archives the older "41 ZOY", and adds sample work in plan order (finished, running and next-up tasks, unplanned tasks, problems) plus two small extra projects for the director's portfolio. It is safe to re-run. `GET /api/projects/{id}/sequence` returns the planned order with what is ready and what each activity is waiting for (negative lags are treated as leads); tasks are listed in that order. The sequence is guidance, not a lock. Directors belong to projects like everyone else; `GET /api/portfolio` lists theirs.

   **Today, Plan B and the daily checklist:** site engineers and site managers land on Today (project managers have it in the menu too). `GET /api/projects/{id}/lookahead` returns today and the next 5 working days (Sundays off) for the caller's towers: work planned for each day, what stops it (an open problem, a task on hold, or work before it in the plan that is not done) and Plan B: running work nothing stops ("add crew") and ready work that can be pulled forward, towers with stopped work first. Each role (site engineer, site manager, project manager, director) also has a short daily checklist done in order with no step skipped (`GET/POST /api/projects/{id}/daily-checklist`); each person ticks their own list for today, and past days are a read-only record. The starter lists are seeded on start-up into `daily_checklist_items`.

   **Notifications and the PM inbox:** the bell (top right) lists what happened that concerns you and links straight to it. Approvers hear when unplanned work needs approval or a problem is reported or resolved; the person who raised something hears the outcome (approved, sent back, delay confirmed or not); directors hear when a confirmed problem moves the project end. Nobody is notified about their own action. `GET /api/notifications` (with `/read-all` and `/{id}/read`) serves them. On the Overview, `GET /api/projects/{id}/attention` is the project manager's "Needs your action" list (approvals, problems to review, blocked tasks, late activities, work that should have started), ordered by urgency; directors get only the escalations. `GET /api/projects/{id}/digest` powers "This week" and the planned versus expected finish, and `GET /api/activities/{id}/detail` powers the activity panel (click a row in Schedule). Reminders are worked out when you open the screen; there is no email or push yet, because that needs a background job.

   **Project cards and the 3D building:** the director's landing page shows one card per project with a photo, progress, what is being built now, late activities, open problems and the expected finish. Photos go in `frontend/public/projects/` (see the README there); until then a simple illustration is shown. Opening a project shows a 3D model of each tower, floor by floor: finished slabs solid green, the slab being built filled to its percentage, the rest outlined, late ones outlined in red (`GET /api/projects/{id}/building`; click a floor for its activity). Floors come from the schedule's slab activities, so a project needs floor-wise slabs for this to appear. Each tower is a plain block until its drawing is added: save the drawing as DXF and run `python scripts/dxf_to_building_model.py drawing.dxf --unit mm --list`, then again with `--project <code> --wing "Tower A=<number>"` (details in `data/models/README.md`). Sample projects (41 Aventis, 41 Westworld, 41 Luxoverts) are named after real Krisala projects; their progress is sample data.

6. Run the FastAPI backend server:
   ```bash
   uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
   ```

### Importing the 41 ZOY Master Baseline

The PDF baseline is stored separately from the live activity schedule. Importing it does not
replace forecast or actual dates, progress, status, approvals, dependencies, or project history.
Run a validation-only pass first, then add `--apply` to persist the baseline dates:

```powershell
.\venv\Scripts\python.exe scripts\import_zoy_pdf_baseline.py "C:\Users\athar\Downloads\ZOY - Baseline Master Schedule Tracker 06-OCT-2026(2).pdf"
.\venv\Scripts\python.exe scripts\import_zoy_pdf_baseline.py "C:\Users\athar\Downloads\ZOY - Baseline Master Schedule Tracker 06-OCT-2026(2).pdf" --apply
```

The importer checks that every PDF task maps unambiguously to an existing 41 ZOY activity.
If a row is unmatched or ambiguous, it stops without applying activity changes. Re-running a
successful import is safe and updates only the stored baseline dates and PDF source metadata.

## 🔒 Geotechnical Intelligence External API (v1)

A dedicated, cryptographically hashed API-key secured namespace under `/api/v1/geotechnical/` for external construction systems (e.g., Construction ERPs, PMIS, Civil engineering software).

### Authentication
Send your provisioned API key in the `Authorization` header:
```http
Authorization: Bearer geo_live_xxxxxxxxxxxxxxxxxxxxxxxxx
```
or via the `X-API-Key` header:
```http
X-API-Key: geo_live_xxxxxxxxxxxxxxxxxxxxxxxxx
```

### Security Features
- **SHA-256 Hashing**: Plaintext keys are never stored in the database.
- **Granular Scopes**: `geotechnical:upload`, `geotechnical:read`, `geotechnical:analyze`, `geotechnical:alerts`, `geotechnical:recommendations`, `geotechnical:admin`.
- **Perimeter Boundary Isolation**: External API keys are strictly confined to `/api/v1/geotechnical/*` and cannot access internal platform modules (`/civil`, `/electrical`, `/admin`, `/users`).
- **Multi-Tenant Isolation**: Complete isolation of reports and data across client tenants.
- **Rate Limiting & Audit Logging**: Sliding 60-second window rate limiting with full request audit logging.

### Endpoints Summary

| Method | Endpoint | Required Scope | Description |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/v1/geotechnical/reports/upload` | `geotechnical:upload` | Upload PDF/DOCX/TXT/XLSX report with automated parsing & unique ID generation. |
| `GET` | `/api/v1/geotechnical/reports/{report_id}` | `geotechnical:read` | Overview with boreholes count, depths, soil summary & alerts. |
